# v1.1.0 遷移計畫：資料層 Supabase → Neon

> 狀態：**規劃中，未開工**。三個待決事項見文末。
> 這份文件只描述做法，不代表已授權執行。

## 為什麼要搬

| | Supabase Free（現況） | Neon Free（目標） |
|---|---|---|
| 閒置行為 | 7 天低活動就**暫停**，要專案擁有者手動 Resume | 不暫停；5 分鐘閒置休眠，查詢時自動醒（數百毫秒） |
| 故障表現 | 網站靜靜地壞掉（2026-11-14 已發生一次，`/api/trees` 回 503 `db_unreachable`） | 第一次查詢慢一點，之後正常 |
| 免費額度 | 2 個 active 專案、500MB DB、1GB Storage | 100 個專案、1GB DB/專案、100 CU-小時/月 |
| 檔案儲存 | 內建 Storage（考察照片在用） | 無同級 Storage → 改用 Vercel Blob（Hobby：1GB、10GB/月） |

## 目標架構

```
Vercel Functions (/api/*) ──► Neon Postgres 17（aws-ap-southeast-1 新加坡）
        │                     @neondatabase/serverless（HTTP driver）
        └──► Vercel Blob（實地考察照片）
```

**刻意不變**：API 路徑與回應格式、前端 12 個分頁、658 筆資料、分級與官方值邏輯、版面。
**刻意移除**：`@supabase/supabase-js`、`SUPABASE_*` 環境變數、RLS（查詢一律經 Serverless API）。
**禁止**：雙寫（同時寫 Supabase 與 Neon）。

## 現況盤點（2026-11-14 查證）

- 程式碼：`lib/repo.js` 898 行；唯一 Supabase 依賴 `@supabase/supabase-js`；9 個查詢點（species／parishes／routes／conservation_topics／timeline_events／v_trees／field_records／`rpc_find_trees`）；Storage 兩處（`repo.js:662`、`repo.js:785`）。
- 資料庫：8 表、3 檢視、6 函式、9 索引，皆為標準 Postgres。
- 測試：29 組 392 項。
- 照片：實地考察紀錄 0 筆 → 無歷史照片需搬遷。
- Neon：組織 `Rimuru`（free），3 個既有專案皆在 `aws-ap-southeast-1`，無 old-trees 專案。
- Vercel 專案 `old-trees` 的環境變數含 7 個 `POSTGRES_*`，是舊整合殘留（Neon 組織內無對應專案），遷移時直接取代，不要沿用。

## 風險與回滾

- **Neon 額度用完**：compute 停到下個帳單週期（資料不刪）。用量估算極低（0.25 CU × 每日十數次喚醒）。
- **Blob 1GB**：單張 60–90KB、每筆最多 3 張；300 筆約 80MB。
- **回滾**：Supabase 專案保留至驗收通過後再刪；環境變數改回即可回到 v1.0.6。
- **安全前提**：Supabase 專案刪除後，2026-09-24 外洩且**目前仍有效**的舊 `service_role` 金鑰才會失效。在那之前 repo 不得轉為 public。
